# Hadrontech BMS — System Map

This document exists to answer one question quickly: **"if I add or change something here, what else needs to know about it?"** It was written after finding the same class of bug three times in one review — a feature gets built in one place (a new field, a new store, a new report) but the surrounding systems that should also reflect it (CSV export, Dashboard, Reports) quietly don't get updated.

There are two things here:
1. **The map** — every data store, which file owns it, and its current integration status.
2. **A companion automated test** — `test-system-connectivity-map.js` — that checks several of these connections *structurally*, by reading the actual source files. Run it after adding any new store, field, or report. It exits with a non-zero code and a clear message if something's disconnected — it does not rely on this document being kept up to date to catch a mistake.

This document should still be kept current by hand, since it explains *why* things are the way they are, which the automated test can't.

### Known gaps (flagged, not fixed — worth a decision, not urgent)
- **Search doesn't cover `enquiries` or `stockMovements`.** Enquiries are short-lived lead records; stock movements are high-volume audit-style entries. It's plausible neither needs to be individually searchable, but this hasn't been explicitly decided — just noting it so it's a deliberate choice rather than an oversight.

### Deliberate non-connections (confirmed correct, not gaps)
- The **printed Supplier PO document** doesn't show payment status. A PO sent to a supplier is a commitment/order document, not a payment record — the supplier doesn't need to see what we've paid them printed on their own copy of the order.
- `counters`, `settings`, and `activity` don't get CSV exports, search entries, or Dashboard tiles — they're internal system bookkeeping, not business records a person would look up.

## Where things live, at a glance

- **Backup & Restore**: `js/backup.js` — `BACKUP_STORES` (what gets included in a full backup) and `CSV_COLUMNS` (what each individual CSV export contains) are two separate lists that must be kept in sync manually. A store can be backed up but have no CSV export column definition (rare, only makes sense for internal stores) — but every CSV column definition should have a matching export button in the Backup & Restore page's UI.
- **Internal-only quotation line columns** (Lead Time, Total Freight for This Line, Unit Cost, Cost Ccy, Rate, Markup %, Supplier, Amount w/ VAT): shown on the edit form and the read-only Detail view, styled with the shared `.internal-only-col` CSS class (amber tint, gives every such column its consistent orange highlight for free — no per-column styling needed), and deliberately never referenced in `print.js`, since these are reference/cost figures for internal use only, not shown on the customer-facing printed document. A new field in this family needs: the column added to both header strings (edit form's `<thead>` and the read-only `lineItemsHead`), a cell in both row-rendering functions, and — if it should come from the product catalog — a copy-through line where `line.leadTime`/`line.markupPercent` are already set when a product is picked. Sales Orders need no separate wiring for these fields: `createFromCustomerPO` copies a Quotation's line objects wholesale (`Object.assign({}, l)`), so any field already on a Quotation line carries through to the Sales Order automatically.
- **Entity engine money fields with a fixed currency** (`js/entities.js`): a `type: 'money'` field on `Entities.defineEntity` normally displays in the record's own `currency` (or `defaultCurrency`) field on the read-only Detail view — correct for something like Standard Cost, which genuinely varies by product (USD from an overseas supplier, PHP from a local one). A field that must always display in one specific currency regardless of the record's own sourcing currency (e.g. Products' Estimated Freight Cost, always PHP since freight into the Philippines is a local cost) sets `currency: 'PHP'` directly on that field's definition — `renderDetailValue` checks for this override before falling back to `record.currency`. Omitting it silently mis-displays the field in whatever currency the record happens to be costed in.
- **Search**: `js/search.js` — a single function that fetches from several stores and searches across them together. Adding a new searchable store means adding it to the `Promise.all` fetch list and adding a results section for it.
- **Dashboard**: `js/dashboard.js` — stat tiles are hand-picked, not automatic. Adding a new store doesn't put it on the Dashboard by itself; someone has to decide it's worth a tile and add one.
- **Reports**: `js/reports.js` — `REPORT_GROUPS` (what shows in the nav, organized by category) and the `buildReport()` switch statement (what each report actually computes) are two separate things that must both be updated together — a report key in one without a matching case in the other either shows nothing or is unreachable dead code.
- **Report text filters (Customer / End-User / Supplier)**: a report opts in by adding `filters: [...]` (any of `'customer'`, `'endUser'`, `'supplier'`) to its entry in `REPORT_GROUPS` — this alone makes the corresponding filter box appear above that report's table, hidden for every report that doesn't list it. Deliberately typeable text (case-insensitive, partial match via the shared `textMatches()` helper), not a dropdown of exact values — real data entry varies in capitalization (`ONSEMI` vs `Onsemi` vs `onsemi`), and a dropdown of distinct strings would silently split one real-world entity into several options, missing whichever variant isn't picked. The report's own `case` in `buildReport()` must actually apply `textMatches(...)` to its rows before computing totals — adding `filters: [...]` to the definition alone does nothing on its own. Rolled out across every report where the underlying data actually has that dimension: Customer + End-User on Quotation-based reports (Quotation Register, Open/Won&Lost/Expiring/Expired, Gross Profit Won-only, Projected Gross Profit, Technical Offers Log — Technical Offers carry both fields too), Customer-only on Sales-Order-based reports (Sales Order Register, Awaiting Delivery, Sales Register Bookkeeper, Payments Aging — Sales Orders have no End-User field), Supplier-only on Supplier-PO-based reports (Supplier PO Register, Purchase Register Bookkeeper, Supplier Payments Aging). Deliberately left off Sales by Customer/Month (already grouped by that exact dimension) and Expense Register/by Category (no customer/supplier/end-user dimension exists on an Expense at all).
- **Report Status filter**: same `filters: [...]` opt-in mechanism, `'status'` this time, but rendered as a real `<select>` dropdown rather than typeable text — Status is a fixed, known enum per entity type (unlike Customer/End-User, there's no free-text capitalization risk), so an exact picker is the right tool here, not `textMatches()`. The catch: there are FOUR distinct, non-interchangeable status enums in this app — `QUOTE_STATUSES` (Quotations), `SO_STATUSES` (Sales Orders), `SPO_STATUSES` (Supplier POs), `TO_STATUSES` (Technical Offers), each exported via `window.X_STATUSES` from its own module. A report supplies its own `statusOptions: () => [...]` function (must be a function, evaluated lazily at render time, not a bare array — `REPORT_GROUPS` is declared before every module has necessarily loaded and set its `window.X_STATUSES`) returning exactly the options relevant to it — sometimes the full enum (Quotation Register, Expired Quotations, Projected Gross Profit — all show every stage with no built-in restriction), sometimes a curated subset (Won & Lost only offers `['Won','Lost']`, Open Quotations only `['Draft','Sent','Under Review']`, Awaiting Delivery only its own two statuses) so the dropdown never offers a choice that could never actually match a row on that report. Deliberately left off reports already filtered along a different, more relevant status-like dimension (Payments/Supplier Payments Aging already filter by payment status, not fulfillment status) or where the underlying set is already 100% one value (Gross Profit Report Won Only).
- **Routing**: most modules call `Router.route('/path', handler)` directly. Customers, Suppliers, and Products are the exception — they go through a shared generic CRUD engine (`Entities.defineEntity({ key: '...' })` in `entities.js`), which registers their `/key`, `/key/new`, `/key/:id`, `/key/:id/edit` routes automatically from that one config object. This matters if you're ever grepping for `Router.route` to check what's registered — these three won't show up that way.

## Data durability (added after a real data-loss incident)

This app has no server — every record lives in the browser's IndexedDB storage only. That makes it vulnerable to a few real, silent failure modes:
- A browser setting like "clear cookies/site data when closed" wipes everything on browser close, with no warning.
- Using a private/incognito window wipes everything when that window closes — by design, not a bug.
- Without persistent storage granted, browsers can silently evict a site's data under disk pressure.

As of the fix for the incident that prompted this section: **the app now requests `navigator.storage.persist()` on every boot**, and shows a visible warning banner if the browser declines (or doesn't support the API at all). This protects against the third scenario, but explicitly does **not** protect against the first two — those are the person's own browser configuration, not something code running on the page can override. The warning banner's text says this directly, so nobody reads "protected" as a guarantee it isn't.

**The practical implication hasn't changed: regular backups are still the only real protection against total data loss.** Persistent storage reduces one risk factor; it doesn't replace backups.

Following the same incident, backups themselves got two improvements:
- **A real save-location picker** (`showSaveFilePicker`, Chrome/Edge): choose a folder once, and it's remembered by the browser for next time — no more hunting through Downloads. Falls back to the normal download behavior on browsers that don't support it (Firefox/Safari). Every backup now uses a standardized filename, `Hadrontech_Backup_YYYY-MM-DD.json`.
- **A proactive backup prompt**, not tied to the unreliable moment of closing the browser at all. `logActivity()` — already called after every significant save across the whole app — is the single central hook: it flags that something's unbacked, and `BackupReminder.maybeShowBackupPrompt()` asks the person, while the app is still fully open and responsive, whether they'd like to back up now. Throttled to once per session so it doesn't nag, and resets after a successful backup so a later batch of new work can still prompt again.

## Currency-handling convention (worth remembering)

Two different, deliberately different rules exist side by side:
- **Customer-facing money** (Proforma Invoices, Sales by Customer/Month) is assumed to always be PHP, since this business sells to Philippine customers. Reports show one clean PHP total, and if a non-PHP record ever shows up, it's flagged as a standalone anomaly worth double-checking — not silently included or averaged in.
- **Supplier-facing money** (Supplier PO payments) genuinely spans currencies — local suppliers bill in PHP, overseas manufacturers (e.g. Pentair) bill in USD. These reports and Dashboard tiles break totals down **by currency**, never combining them into one blind sum.

If you're ever adding up money across multiple records, ask first: is this customer-side (assume PHP, flag exceptions) or supplier-side (break down by currency, never combine)? Mixing these two conventions up is exactly the class of bug this system has hit before.

## Checklist for adding something new

When adding a new store, or a meaningful new field (especially a status or a financial figure) to an existing one:

1. **New store?** Add it to `BACKUP_STORES` and give it a `CSV_COLUMNS` entry + export button, unless it's purely internal system data.
2. **New status field?** Give it a color-coded badge (reuse an existing color group in `styles.css` if the semantics match — Draft/grey, in-progress/blue, needs-a-decision/amber, done/green — before inventing a new color). Check whether it should show up in any Reports table with `badge: true`.
3. **New financial figure?** Decide: customer-side (PHP-assumed) or supplier-side (multi-currency) — see above. Check whether an existing CSV export or Dashboard tile now needs updating to include it, the same way Proforma Invoices' and Supplier POs' CSV exports needed updating after payment tracking was added to each.
4. **New report?** Add it to both `REPORT_GROUPS` (which category it belongs under) and a matching `case` in `buildReport()`.
5. **Run `node test-system-connectivity-map.js`** before considering the work done. It won't catch everything (it checks structure, not business logic), but it catches exactly the class of mistake that prompted this whole document.

- **Line freight model (quotations):** a line with `freightMode: 'total'` stores `estimatedFreightCost` as the TOTAL freight for the whole row, in the row's cost currency. Freight/unit = total ÷ qty (0 when qty is 0); landed unit cost = (unit cost + freight/unit) × rate; calculated selling price = landed × (1 + markup%); line cost = (unit cost × qty + total freight) × rate. Helpers live at the top of `quotations.js` and are exported on `QuoteCalc` (`lineFreightPerUnit`, `lineLandedUnitCost`, `lineCalcPrice`, `convertLegacyFreight`). Lines saved before this change have no `freightMode`: they keep their old per-unit math, are flagged "review", and only change through the explicit "Convert to line total" button. A typed Unit Price sets `priceOverridden` and is never silently replaced (flagged, with "Use calculated"). On Products, "Estimated Freight Cost" + "Freight Covers Qty (pcs)" (default 1; missing/0 = 1, so old products keep their per-unit meaning) give per-unit freight = amount ÷ qty covered (`productFreightPerUnit`); picking a product sets line total = per-unit × line qty. "Split shipment freight…" on the quotation form (`allocateFreight`, exported on `QuoteCalc`) splits one supplier shipment total across chosen rows of the same cost currency — by cost (default), quantity or manual — in whole cents that always sum exactly to the shipment total; rows keep a `freightNote` until their freight is edited by hand. The header Freight / Shipping Charge is billed on top of line prices, so the form shows how much freight is already built into line prices.

- **Catalog-sourced line freight:** a line whose freight came from picking a product carries `freightSource: 'catalog'` + `catalogFreightPerUnit`, so its total freight follows the line quantity (per-unit rate × qty). Typing the freight, applying a shipment split, or changing the Cost Ccy hands control to the user (the source is cleared and the total then stays fixed on qty changes).

- **Project Packages (Products & Services):** Type = "Project Package" in New Product creates one catalog item numbered `ITEM-P-0001` (own counter `projectPackage`; normal items keep `ITEM-00001`) that carries its component items INSIDE the same record as `components[]`, numbered per project `ITEM-P-0001-01`, `-02`… (`nextCompSeq` per package; a number is never reused after a delete). Components therefore never appear as rows in the Products list, and the product's type is locked after creation. Selecting a package in a quotation's Select Item replaces that row with a **package (lot) line** (`lotRole: 'header'`, qty 1, UOM lot, suggested price = components' cost + freight + markup, editable) plus one **component line** each (`lotRole: 'component'`, cost and catalog-rate freight, price 0, prints blank, never auto-priced). Gross profit therefore = lot price − all component costs. Generic entity-engine hooks added for this: `counterFor`, `beforeSave`, `afterNumber`, and `afterFormRender(form, record)`.
  - **Package supplier, lead time, warranty & lot membership:** a package has ONE supplier (`defaultSupplierId`, required) who quotes all items, plus Lead Time and Warranty "as per the package". Category / Manufacturer / Brand / Model / UOM are not used by packages (hidden; saved empty, UOM `lot`). **The package itself is never a quotation line**: picking it adds only its component lines (ITEM-P-0002-01, -02, …), each with the package supplier and lead time, and fills the quotation's Warranty (and Delivery Lead Time if empty). Each component loads priced at cost + freight + markup; one that works out to zero (e.g. "as detailed below" items) stays blank (`lotRole:'component'`, prints blank = part of the lot line above it; its Disc. also prints blank, on screen the Disc. box is blank and disabled until a price is typed). Typing a price makes it priced on its own; clearing it makes it blank again ("Price it separately" in its "!" popup). `refreshPackageNote()` shows a "Project: ITEM-P-… name" reference above the lines, plus an orange reminder when blank items still carry a cost ("Items 03, 05 have a cost but no price…"). Older quotations that already contain a synthetic lot line (`lotRole:'header'`) still open and work; new ones never get one. The old per-item `pricing` setting is ignored on load. Test: `test-project-package-mixed-pricing.js` (includes the full chain to a Supplier PO).
  - **Price review popup:** long price messages (manual price vs calculated + "Use calculated", lot price differs + "Use that") live in a hidden `.ln-price-info` holder shown in a popup by the orange "!" `.ln-flag-btn` beside Unit Price; only short labels ("In lot price", "Lot items: ₱X") stay under the price. The note under Freight / Shipping Charge was removed (`#freightInfo` is now always empty).

- **Supplier PO freight & listing link:** creating a Supplier PO from a Sales Order pre-fills `freight` with the selected lines' total freight (`suggestedPOFreight`; old per-unit lines = per-unit × qty; lines whose cost currency differs from the PO/supplier currency are NOT converted — counted in `freightSkippedLines` and noted). `freightEstimate` keeps the quotation figure so the PO shows "Quotation estimate: X" next to the real freight once it is edited. Item rows on the PO detail and edit pages show an "Open listing ↗" link (new tab, `noopener`, http/https only) read live from the product's Supplier Listing URL via `itemId`. Test: `test-supplier-po-freight-and-listing-link.js`.

- **No dead links (`test-no-dead-links.js`):** crawls every page from the sidebar, follows every internal link/breadcrumb, and fails on "Page not found" / "not found" / error pages — with full data, then again after deleting the quotation, customer PO, supplier, product and customer. It also checks that every `navigate()` / `href="#/…"` target in the code matches a real route, that detail and edit pages for a missing record show a plain "X not found" message with a way back (never "Something went wrong"), and that every external link opens in a new tab with `noopener`. `enquiries.js` is dormant (not loaded) and is skipped. When adding a page or link, run this test.

- **Project Package items are not stock items.** Lines with a package component number (`compNo`) ship straight through: receiving a Supplier PO or recording a Sales Order delivery posts NO stock movement for them (previously they piled receipts/deliveries on the package record, mixing pcs and metres, and could block a delivery with a false "only 0 in stock"). The panels label them "project item — not kept in stock". Supplier PO lines now carry `compNo`. Sales Order and Proforma Invoice prints leave Unit Price and Amount blank for blank-price lines, like the quotation. Test: `test-e2e-project-package-to-proforma.js` (package → quotation → customer PO → SO → Supplier PO → receive/pay → delivery → Proforma → payments, plus a mixed normal-item + package order with two suppliers).

- **Payslips (Distributions).** Each partner split on a Distribution can print a payslip (`Print.printPayslips(dist, idx)`; `idx = null` prints every partner, one page each). Number = distribution number + the split's own stable `slipSeq` (e.g. `HT-DIST-2026-0003-02`, kept even if other rows are removed). Shows the month's business results (Gross Profit → Expenses → Net Profit → Reserve → Distributable) and ONLY that partner's own share; never other partners' amounts. "Payslip details" on the Distribution page records advances/deductions/additions (`adjustments[]`, kind `less`/`add`), date paid, method and reference; `netPay = share + additions − deductions` (refused if negative). These ride on each split and are preserved when the Distribution is edited. Older distributions without payslip data print fine (numbered by row). Test: `test-payslips.js`.
- **Partners & Employees.** The Partners module (route `/partners`, store `partners`) now has a Type (`Partner` / `Employee`), "Position / Role" and "Default Share %"; the Distributions button reads "Manage Partners & Employees". Payslip rule (`Print.printPayslips`): an **Employee** payslip shows only name, position, payment details, one earnings line ("Incentive for <month>"), adjustments and Net Pay, never Gross/Net Profit, Expenses, Reserve, Distributable Amount or the share %. A **Partner** payslip also shows the business results. The person's CURRENT type wins over the snapshot saved on the split, so switching someone to Employee limits their older payslips too. Print windows now have styled Print and Close buttons.
- **Business Reserve.** Settings → Defaults & Terms has `defaultReservePercent` (default 10): every new Distribution starts with it (editable per distribution; edits keep their saved %). Reserve **balance** = sum of every Distribution's `reserveAmount` minus `settings.reserveWithdrawals[]` (money taken out: date, amount, required reason; cannot exceed the balance; entries can be removed). Recorded from Distributions → "Use Reserve"; shown on the Distributions page (Balance / Set Aside / Used) and the Dashboard "Business Reserve" tile. Withdrawals live in the settings record, so they are in the normal backup. Test: `test-business-reserve.js`.
